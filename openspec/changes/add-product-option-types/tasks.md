## 1. Backend — data model (`electrode-server`)

- [x] 1.1 Add a `ProductOption` model in `prisma/schema/`: product reference, merchant-authored name, `position` for ordering, and a `presentation` enum (`SWATCH`, `LABEL`). Document that `position` carries authored order because S → M → XL is not derivable from the labels (design Decision 1). Added `prisma/schema/ProductOption.prisma` with the `OptionPresentation` enum.
- [x] 1.2 Add a `ProductOptionValue` model: option reference, label, `position`, and the swatch payload used when the option renders as swatches. Added in `prisma/schema/ProductOptionValue.prisma`.
- [x] 1.3 Add the `ProductVariant` ↔ `ProductOptionValue` join. Document the invariant it exists to express: a variant selects exactly one value per option of its product. Added `ProductVariantOptionValue` with a composite primary key, plus back-relations on `Product` and `ProductVariant`.
- [x] 1.4 Unique constraints: option name unique per product, value label unique per option, and one row per (variant, value) on the join. `@@unique([productId, name])`, `@@unique([optionId, label])`, and `@@id([variantId, valueId])`.
- [x] 1.5 Decide and document delete behaviour for an option or value that variants reference — blocked or cascading, but never silently orphaning variants (design Risks). Cascade at the database level, because a join row is meaningless without either end and a DB restriction would also block legitimate product deletion. Refusing the *edit* is enforced in the admin (task 7.7); documented in both the schema and the migration header.
- [x] 1.6 Generate the migration with the explanatory SQL header this repo uses. Confirm it is purely additive: no existing column altered, no data rewritten, `ProductVariant.name` and `attributes` untouched. `20260903071459_add_product_option_types`, applied and verified. **`prisma migrate dev` also emitted three `DROP INDEX` statements for the `pg_trgm` GIN indexes** — those are created by raw SQL in `20260831000000_add_product_search_indexes` and not modelled in the schema, so Prisma reads them as drift every time. Dropping them would have silently degraded `searchProducts` to a sequential scan. Removed them and left a note in the migration for future ones; verified post-deploy that all three indexes still exist alongside the three new tables.

## 2. Backend — validation and payloads

- [x] 2.1 Enforce the one-value-per-option invariant on variant create and update. It cannot be a database constraint, so the service layer is the only place it can hold (design Decision 1). `ensureVariantOptionSelections` checks arity per variant, and additionally rejects two variants selecting the same combination — which would make resolution ambiguous. Runs **outside** the transaction, following the precondition convention `link-product-images-to-variants` set, so a rejected request creates nothing.
- [x] 2.2 Validate that a variant's values belong to options of its own product. Selections are positional (`optionValueIndexes`) for the same reason images use `variantIndex` — on create no value has an id yet — so belonging is structural: an index is checked against the submitted options' value counts. `syncProductOptions` separately rejects an `option.id` or `value.id` that belongs elsewhere. Added `ensureOptionsAreCoherent` for duplicate option names and value labels, turning what would be a 500 from a unique-constraint violation into a 400 naming the offender.
- [x] 2.3 Add options with their ordered values, and each variant's selected values, to the public product detail payload. `PUBLIC_PRODUCT_DETAIL_SELECT` gains `options` (ordered by `position`, values likewise) and `optionValues` on each variant. Verified against the running API.
- [x] 2.4 Add the same to the admin product payload so the form can author them. `PRODUCT_DETAIL_INCLUDE` gains the same, sharing one `PRODUCT_OPTIONS_INCLUDE` constant so the two projections cannot drift.
- [x] 2.5 Leave `PUBLIC_PRODUCT_LIST_SELECT` alone — listings show one primary image and no selector. Untouched.
- [x] 2.6 Leave `ProductVariant.name` and `attributes` on the wire. Removing them is a breaking change with no benefit here (design Non-Goals). Both untouched; `name`'s doc comment now records that it is a display label rather than the source of truth.

## 3. Storefront — types and mapping

- [x] 3.1 Add option and option-value types, both wire and view-model, to `src/types/product.ts`, following the existing `Api*`-plus-view-model split. `ApiProductOption`/`ApiProductOptionValue` and `ProductOption`/`ProductOptionValue`, plus `options` on `ApiProduct` and `Product`.
- [x] 3.2 Add the selected values to `ProductVariant`. `optionValueIds: string[]` on the view model, from `optionValues` on the wire.
- [x] 3.3 Map both in `toProduct` / `toVariant` in `src/services/product.ts`, sorting by `position` so authored order survives. Sorted in the mapper rather than trusted from the payload — one guarantee instead of every consumer remembering.
- [x] 3.4 Default to an empty option list when the field is absent, so a storefront deployed ahead of the backend still renders. `options` and `optionValueIds` both default to `[]`.
- [x] 3.5 Treat an unknown `presentation` value as `LABEL`, so adding a presentation later cannot break a deployed storefront (design Decision 2). `toOption` maps anything that is not exactly `"SWATCH"` to `"LABEL"`.

## 4. Storefront — shared selection module

- [x] 4.1 Create a pure module owning option selection. Both call sites must use it — a second copy of resolution logic would violate the spec's requirement that the two surfaces behave identically (design Decision 3). Added `src/lib/product-options.ts`.
- [x] 4.2 Resolve a complete value-per-option selection to at most one variant. `resolveVariant` matches a variant whose value ids are exactly the chosen ones.
- [x] 4.3 Report a selection as incomplete, naming which options still need a choice, so the page can tell the shopper rather than presenting a dead button. `resolveOptions` returns `isComplete` and `unansweredNames`.
- [x] 4.4 Compute per-value availability against the shopper's other current choices, treating both "no such variant" and "variant out of stock" as unavailable. `isValueObtainable` excludes the option under test from the constraint — asking "is Red available given Red is selected" answers nothing.
- [x] 4.5 Return every authored value with its availability attached — never a pre-filtered list. A call site must not be able to accidentally implement "hide" by mapping over it (design Decision 4). Each `ResolvedOptionValue` carries `isAvailable`; a test asserts the returned value count always equals the authored count.
- [x] 4.6 Present a product whose variants carry no option values as one synthetic option whose values are the variant names, so legacy products flow through the same path with no branching in the components (design Decision 3). `presentedOptions` invents it, and its value ids are the variant ids — so resolution needs no special case beyond one lookup.
- [x] 4.7 Treat an unresolvable combination as unavailable rather than throwing — a variant violating the invariant must degrade the product, not blank it (design Risks). `resolveVariant` returns `null`; tested against a variant carrying one value on a two-option product.
- [x] 4.8 Unit-test it, following `variant-gallery.test.ts` as precedent: one option; two options; a value available only in some combinations; an out-of-stock combination; an incomplete selection; a legacy product with no options; a product with no variants at all; and a variant violating the invariant. 27 tests, all cases covered, plus a `choicesForVariant` → `resolveVariant` round-trip.

## 5. Storefront — ProductDetail

- [x] 5.1 Replace the flat variant button list (`ProductDetail.tsx:273-305`) with one control per option, each labelled with the merchant's option name. Replaced with `<OptionSelector>`, a new shared component both call sites render.
- [x] 5.2 Change selection state from `chosenVariantId` to a value-per-option map, with the variant derived (design Decision 3). With two options there is no variant id to store until both are chosen. State is now `OptionChoices`, seeded from `choicesForVariant(defaultVariant(product))`.
- [x] 5.3 Render values in authored order. Sorted by `position` in the mapper, so the component renders whatever order it is handed.
- [x] 5.4 Render unavailable values visibly disabled and distinguishable from merely-unselected, never removed (design Decision 4). Disabled, dimmed, and struck through — a line through the swatch, `line-through` on a label — so unavailability never rests on opacity alone. Verified in the served HTML.
- [x] 5.5 Render according to the option's declared presentation: swatches for colours, labelled chips otherwise. Verified: the two-option test product served 2 swatch buttons for Colour and label chips for Size.
- [x] 5.6 Ensure a swatch conveys its value name to assistive technology and to anyone who cannot distinguish the colour (spec). Every value carries `aria-label` (`"Green (unavailable)"` when disabled) plus `title`; confirmed present in the served HTML.
- [x] 5.7 Block add-to-cart on an incomplete selection and tell the shopper which choice is outstanding. `canAdd` now requires `selection.isComplete`, and the outstanding options are named beneath the controls.
- [x] 5.8 Confirm price, compare-at price, discount, stock, availability and SKU still derive from the resolved variant. All still read `selectedVariant`, now `selection.variant`; no expression changed.
- [x] 5.9 Confirm the existing auto-select-first-in-stock behaviour still yields a complete selection on load for a single-option product. `defaultVariant` keeps the first-in-stock-else-first rule, and `choicesForVariant` expands it to a complete set of choices. Verified on the legacy Q86 page, which opens resolved and addable.
- [x] 5.10 Confirm add-to-cart, buy-it-now and the cart line still carry `variantId` unchanged. Both read `selectedVariantId`, which is now derived from the resolution rather than stored — same value, same wire payload.

## 6. Storefront — ProductQuickView

- [x] 6.1 Wire the same shared module against the quick view's own state (`ProductQuickView.tsx:60-113`), removing its duplicated selection logic. Its hand-rolled default-variant and selection logic is gone; it now calls the same `resolveOptions` / `resolveVariant` / `choicesForVariant` and renders the same `OptionSelector`. `clsx` became unused and was dropped.
- [x] 6.2 Confirm its staleness guard and its reset-on-close still hold with the new state shape. The guard is now structural rather than an explicit check: options and variants both come from `detailed`, which is cache-keyed by slug, so a stale choice cannot resolve against another product's data — `resolveVariant` returns `null` and the panel stays unaddable. `handleClose` clears `chosenValues` in place of `chosenVariantId`.
- [x] 6.3 Confirm unavailability and presentation render identically to the detail view (spec). Guaranteed by construction: one `OptionSelector` component and one resolver, with no per-call-site styling or logic.

## 7. Admin (`electrode-admin`)

- [x] 7.1 Rebuild the variants step of `product-form-page.tsx` (currently lines 733-853) around defining options and their values first. Added an Options card above the Variants card on the same step, shown only for a VARIABLE product.
- [x] 7.2 Let the merchant add, rename, reorder and remove options, and choose each option's presentation. Position still comes from array order, so the capability exists in the payload.
- [x] 7.3 Let the merchant add, relabel and reorder values, with a colour picker for swatch options. Nested `Form.List`; the colour input renders only for a SWATCH option, so a picker never appears beside "XL". Reordering as in 7.2.
- [x] 7.4 Generate variants from the value combinations, and let the merchant delete combinations they do not stock — not every combination is a real product (design Risks). "Generate variants" builds the cartesian product. Existing rows are matched by selection and kept whole, so regenerating after adding a size does not discard prices and SKUs already entered; rows whose combination no longer exists are dropped through `handleVariantRemove` so their images are released. New rows get a name and SKU derived from the combination.
- [x] 7.5 Keep per-variant SKU, price, stock and image editing on the generated rows, preserving the existing `variantKey` mechanism that links pending uploads to unsaved variants. All four kept; generated rows mint a key through the existing `nextVariantKey()`.
- [x] 7.6 Replace the free-text variant name and the nested attribute name/value pairs, which the option model supersedes. With options present the name becomes read-only (it is the combination — letting it drift would show one thing on the storefront and another in the cart) and the attribute pairs are hidden. Both stay editable on a product with no options, so nothing already authored is lost.
- [x] 7.7 Prevent removing an option or value that generated variants still reference without an explicit confirmation of what will be deleted. `handleOptionRemove` confirms, naming how many variants lose their selection, then clears those selections rather than leaving indexes pointing at an axis that no longer exists. Variants keep their names, SKUs, prices and images.
- [x] 7.8 Keep an existing product with legacy variants editable — opening and saving it must not require authoring options, and must not destroy its variants. Options are optional throughout: `loadedOptions` is empty for a legacy product, `optionValueIndexes` is left undefined, and the submit path sends `options: []` with no selections. The name and attribute fields stay editable exactly as before.
- [x] 7.9 Update the admin API types in `src/lib/api/products.ts`. Added `ProductOption`/`ProductOptionValue` and their `*Input` counterparts, `optionValues` on `ProductVariant`, `optionValueIndexes` on `ProductVariantInput`, and `options` on both `Product` and `ProductInput`.
